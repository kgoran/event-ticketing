# M2 demo runbook (about 20 minutes, one presenter, one laptop)

The system in a Kubernetes cluster on the laptop, from [the M2 plan](../milestones/m2.md#demo-script-about-20-minutes-one-presenter):
several instances, scaled by hand and by an autoscaler, a feature flag switched while it runs,
and releases rolled out under load, refused during an on-sale. The `lab` workflow runs the same
steps on every pull request that changes how the system is deployed, and every night
(`M2DemoDryRunTests`, the deploy gate and `deploy --load`), so if it is green, the demo works.
Nothing needs the internet once `lab up` has run (D19).

## The day before (online)

1. Docker Desktop running, with at least 8 GB for its virtual machine. Stop the AppHost if it runs:
   the lab answers on the same ports.
2. Pull the latest `main`, then:
   ```
   dotnet run lab.cs -- up
   ```
   From nothing about 8 minutes: kind, kubectl and Helm, the platform's charts and images, nine
   images of our own. Everything is cached for the next run.
3. `dotnet run lab.cs -- check` says "The lab works." Optional: the dry run on your machine,
   `LAB_SYSTEM_TESTS=1 dotnet test --project tooling/tests/Lab.SystemTests` (about 10 minutes).

## On the day

```
dotnet run lab.cs -- up       # about 1 minute if the cluster is still there
dotnet run lab.cs -- reset    # a fresh database and the demo on sale now, about 2 minutes
```

`reset` puts the demo on sale *now*, which step 7 needs. Open, in this order: Grafana
at http://localhost:3000 (the Aspire Dashboard until M3), the fan site at http://localhost:5100, Mailpit at
http://localhost:8025, the Scaling Lab at http://localhost:5300, and a terminal.

| # | Do | Show |
|---|---|---|
| 1 | `dotnet run lab.cs -- status` | What runs where: the platform (Traefik, CloudNativePG, Keycloak, KEDA, metrics-server), the product with several instances of PublicApi, WebhookIngress and Workers, the tooling. The same addresses as under Aspire |
| 2 | Grafana → **Services**, then Explore → Tempo | Each instance as its own line (the **Instance** picker); a request's trace names the instance (`service.instance.id`) |
| 3 | Fan site: sign in as ana, **Demo Concert**, two seats, **Hold**, **Check out**, **Approve** on LocalPay; then Mailpit | Exactly as under Aspire: confirmed, tickets, the email. The trace crosses instances: PublicApi, WebhookIngress and Workers, each one of several |
| 4 | Scaling Lab: **Rate** 100, **Holds** 20%; **+** twice, then **−** three times | Five instances, then two: chips go ▲ then ✓, or ✕. **Failed** stays at 0. Why it works: readiness that waits for the warm-up, a 5-second `preStop`, a connection budget ([the lab](../lab.md#three-things-the-lab-taught-on-its-first-day)) |
| 5 | **Auto** on; **Step 50 → 150**; after a minute **Stop** | The line under the instances shows the autoscaler's sum (`1 × 1.60 ÷ 0.5 = 3.2 → wants 4`). Instances come within about a minute and go 30 s after the load. Failed stays at 0. Then ask: why does a hold-heavy mix want more instances, and why don't they help? (Requests in progress include waiting for the database's locks, since M3) |
| 6 | **Holds** 50%, **Rate** 40; in the terminal `dotnet run lab.cs -- flag PauseHolds on`; a minute later `… off` | Within about a minute **Refused** jumps and OK halves: new holds get "paused for a moment" (503, Retry-After), browsing goes on, no deploy, no restart. The fan site shows the message if you try to hold |
| 7 | `dotnet run lab.cs -- deploy` | **Refused**: Demo Concert went on sale minutes ago, so no release until an hour after (DP4) |
| 8 | `dotnet run lab.cs -- deploy --restart --load 100 --during-on-sale "the demo"` | The emergency release: every host rolled out again under 100 requests/s, and the count at the end, **0 failed** (T10 allows 0.1%). In the Scaling Lab meanwhile: chips replaced one by one |
| 9 | [database changes](../database-changes.md), the table at the end | The column renamed in one release failed 26% of requests during its rollout; in two releases, none |

Rate and holds go back to 0 with **Stop**; switch **Auto** off before you scale by hand again.

## Afterwards

`dotnet run lab.cs -- down` deletes the cluster and everything in it. Or leave it: `up` the next
day takes a minute.

## If something goes wrong

| Symptom | Cause, and what to do |
|---|---|
| `up`: "Port … is in use" | The AppHost runs: stop it |
| A chip stays ▲ for long | Readiness waits for the database and the warm-up; `kubectl --context kind-eventticketing get events -n eventticketing` |
| Auto doesn't add instances | metrics-server needs about a minute after `up` before it has CPU figures; the line under the instances says "waiting for its first measurement" until then |
| The flag doesn't take | Kubernetes takes up to about a minute to update the file in each instance; `dotnet run lab.cs -- flag` shows what the ConfigMap says |
| `deploy` refused although it should go | An on-sale opened or opens within 30 minutes; `--during-on-sale "<why>"` |
| Anything else | `dotnet run lab.cs -- check` names what fails; `reset` gives a fresh database in about 2 minutes |
