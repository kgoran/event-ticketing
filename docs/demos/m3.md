# M3 demo runbook (about 30 minutes, one presenter, one laptop)

The system keeps serving when a part of it fails, and the door works without the network: from
[the M3 plan](../milestones/m3.md#goal). Three zones with a database instance in each, browsing
that needs no primary, Grafana for every service, the autoscaler on its proper signal, a crash of
the primary under load, the scanner admitting tickets offline, 200 door devices at once, and a
backup restored. The `lab` workflow runs the same steps on every pull request that changes how
the system is deployed, and every night: `M3DemoDryRunTests` (steps 1, 3 and 8), the failover and
zone drills (steps 5 and 6), T8 (step 9) and the backup and restore check (step 10). If it is
green, the demo works. Nothing needs the internet once `lab up` has run (D19).

## The day before (online)

1. Docker Desktop running, with at least 10 GB for its virtual machine. Stop the AppHost if it
   runs: the lab answers on the same ports.
2. Pull the latest `main`, then:
   ```
   dotnet run lab.cs -- up
   ```
   From nothing about 10 minutes: kind, kubectl and Helm, the platform's charts and images, ten
   images of our own. A cluster made before M3 has one node: `down` first. Everything is cached
   for the next run.
3. `dotnet run lab.cs -- check` says "The lab works." Optional: the dry run on your machine,
   `LAB_SYSTEM_TESTS=1 dotnet test --project tooling/tests/Lab.SystemTests` (about 12 minutes).
4. In VS Code, the REST Client extension, for `product/src/Hosts/CheckInApi/CheckInApi.http`.

## On the day

```
dotnet run lab.cs -- up       # about 1 minute if the cluster is still there
dotnet run lab.cs -- reset    # a fresh database and the demo on sale now, about 2½ minutes
```

Open, in this order: Grafana at http://localhost:3000, the fan site at http://localhost:5100, the
Scaling Lab at http://localhost:5300, the scanner at http://localhost:5104/scanner/ (a window of
its own, with the browser's developer tools at hand), `CheckInApi.http`, and a terminal.

The Purchases dashboard counts it |
| 3 | Scaling Lab: **Rate** 200, **Holds** 0%. | 4 | **Auto** on; preset **Step 50 → 150**; after two minutes the preset **Slow database** | The autoscaler adds instances within a minute on requests in progress (`1 × 1.60 ÷ 0.5 = 3.2 → wants 4`), no failed request. Then 50 ms on every database call: holds' p99 climbs to about 500 ms, the autoscaler goes to its maximum, and it doesn't help: the instances are waiting, not working. **Stop**, **Auto** off |
| 5 | **Rate** 60, **Holds** 20%. **Database** panel → **Crash the primary**, click twice | A standby takes over after about 25 s on a new timeline; all three instances are healthy again after about 45 s. The chart: holds fail while there is nowhere to write; **browsing goes on** (2 of 7,106 failed in the drill). Then `dotnet run lab.cs -- check --invariants`: every rule holds |
| 6 | Optional (3 minutes): `dotnet run lab.cs -- drill zone` | A zone's node stops under load: Kubernetes notices after about 40 s, the hosts move, the database's instance waits for its node, which starts again at the end |
| 7 | Fan site, still signed in as ana: `dotnet run lab.cs -- deploy --restart --during-on-sale "the demo"`; reload the fan site during and after | Every host rolled out again; ana stays signed in on whichever instance answers: tokens and keys are in Valkey (D54) |
| 8 | `CheckInApi.http`: **olga**, the event, **olga registers a door device**; copy the response. Scanner: paste it, **Connect**. Then **ana**, **Each ticket's code**: paste the first code, **Check**; the same again; developer tools → Network → **Offline**, paste the second code; **Online** again | The door list arrives with the event's keys. **ADMIT** in milliseconds; then **REFUSE**: "Already let in at …". Offline, the badge says **Offline** and the second ticket is still admitted: the signature is checked with the event's public key, on the device; the scan waits in the queue and uploads within 5 s of going online. Reload the page offline: it comes back from its cache with its list (a PWA) |
| 9 | `CheckInApi.http`: **adam**, **adam revokes ana's third ticket**; paste the third code into the scanner within about 10 s | **REFUSE**: "Revoked". The revocation reached CheckIn through the outbox, and the door with its next sync. Then in the terminal: `dotnet run --project tooling/lab/DeviceSimulator -- --devices 200 --seconds 60`: 200 doors syncing every 5 s, 99% of answers within 500 ms, a revocation at all 200 within about 5 s (T8) |

Then the orders and tickets counted at a named point in the WAL, the backup and the WAL restored into a new cluster in about 50 s, and the same counts there. ana's three tickets are in it |

**Stop** in the Scaling Lab after each step with load; switch **Auto** off before you scale by hand.

## Afterwards

`dotnet run lab.cs -- down` deletes the cluster and everything in it. Or leave it: `up` the next
day takes a minute.

## If something goes wrong

| Symptom | Cause, and what to do |
|---|---|
| `up`: "Port … is in use" | The AppHost runs: stop it |
| `up`: "The lab cluster has 1 node(s)" | A cluster from before M3: `down`, then `up` |
| Grafana shows no data for a minute | Prometheus scrapes every 15 s and the dashboards average over a minute: wait, or widen the time range |
| The scanner says "CheckInApi refused these credentials" | The device was revoked, or the JSON pasted isn't the registration's answer: register another |
| A code is refused: "A ticket for another event" or "Not signed by this event's key" | It is from another event, or was cut short when copied: copy the whole `code` value |
| The revoked ticket is still admitted | The scanner hasn't synced yet (every 5 s, online only): wait a few seconds and check again |
| The crash's numbers differ | Load matters: 60 requests/s with 20% holds is what the numbers above are for |
| `restore-check`: "No backup has completed yet" | `dotnet run lab.cs -- backup` first; `reset` made a new database, and its first backup takes a minute |
| Anything else | `dotnet run lab.cs -- check` names what fails; `reset` gives a fresh database in about 2½ minutes |
