## Goal

The system that runs under Aspire also runs in a local Kubernetes cluster, built from the current
source by one command: **`dotnet run lab.cs -- up` → images → cluster → platform → product and
tooling → seeded demo**. The stateless hosts run as several instances behind a gateway, and the
Scaling Lab shows them and changes their count. A release is a set of images that a pipeline rolls
out under load without errors (T10) and never during an on-sale.

| D22 | **The lab cluster is made by the `kind` tool**, pinned and downloaded by the lab script, not Docker Desktop's built-in Kubernetes. Revises [ADR-0020](../adr/0020-local-kubernetes-on-docker-desktop.md) | The lab is created and deleted by a script ([ADR-0022](../adr/0022-disposable-lab-environment.md)); Docker Desktop's cluster is switched on by hand in its settings and needs a Docker sign-in. | D24 | **The lab script is a .NET 10 file-based app, `lab.cs`** (`dotnet run lab.cs -- up`), instead of PowerShell 7. Revises [ADR-0022](../adr/0022-disposable-lab-environment.md) | Needs only the .NET SDK on Windows and Linux; PowerShell 7 isn't on the presenter's laptop, and Windows PowerShell 5.1 differs from it; the team writes C# | PowerShell 7 (the ADR's choice; listed there as the swap); bash |
| D25 | **Images reach the cluster with `kind load`**, tagged in the lab with a hash of the sources they're built from (committed or not; refined while building LAB2), on the plain `noble-chiseled` base. Updates [ADR-0029](../adr/0029-container-image-per-host.md) | Verified 2026-10-21: PublicApi built in 38 s, loaded in 9 s, runs as non-root. | D26 | **Helm**: the product chart in `product/deploy/chart` with `values-lab.yaml`, the tooling chart in `tooling/deploy/chart`, the platform from pinned upstream charts plus a few manifests; Helm is downloaded like kind | [ADR-0021](../adr/0021-product-tooling-platform-separation.md) puts a chart in `product/deploy`; one template serves every host | Kustomize (no templating for the per-host repetition); plain manifests |
| D27 | **Platform in M2:** Gateway API and Traefik, CloudNativePG with one instance, Keycloak (dev mode, the same realm file as Aspire), Mailpit, metrics-server, and the standalone **Aspire Dashboard** as the telemetry sink. [ADR-0053](../adr/0053-the-lab-cluster-addresses-identity-and-platform.md) | Enough to run and watch every flow; the team knows the dashboard, and it shows each instance separately. The full observability stack comes with M3's service dashboards ([ADR-0016](../adr/0016-teaching-milestones.md)) | Prometheus, Grafana, Loki and Tempo now (2–3 GB more, not needed until M3) |
| D28 | **The same addresses as under Aspire:** every UI and API on its usual localhost port (fan site 5100, PublicApi 5101, …, Keycloak 8180, Mailpit 8025, Scaling Lab 5300), through the cluster's port mappings to Traefik. [ADR-0053](../adr/0053-the-lab-cluster-addresses-identity-and-platform.md) | `.http` files, runbooks and the realm work unchanged; Aspire and the lab can't run at the same time | Host names (`*.localhost` doesn't resolve for non-browser clients on Windows); one port with path prefixes (breaks sign-in redirects and absolute links) |
| D29 | **One token issuer, `http://localhost:8180`:** Keycloak's public address; services inside the cluster reach Keycloak by its internal name, and its discovery document tells them where. No product change. [ADR-0053](../adr/0053-the-lab-cluster-addresses-identity-and-platform.md) | Tokens from the browser, the seeder and the load generator validate everywhere | Different issuers per network (needs product changes and breaks tokens across them) |
| D30 | **Instances in M2:** PublicApi 3, WebhookIngress 2, Workers 2, the rest 1. Set in `values-lab.yaml` | PublicApi and WebhookIngress keep no state; Workers' relay and scheduler already claim rows with `SKIP LOCKED` ([ADR-0014](../adr/0014-outbox-inbox-scheduler-on-postgresql.md)), so two instances show competing consumers. | D31 | **The Scaling Lab shows instances:** per host, the instances wanted and ready, and for each one its age, restarts and state, from the Kubernetes API by label; PublicApi's count can be changed from the lab, the hand-operated version of M5's autoscaler. | D32 | **The Migrator runs as a Helm hook Job before every install and upgrade**; the hosts start only after it succeeds. Updates [ADR-0008](../adr/0008-hosts.md) | ADR-0008 and ADR-0016: several instances migrating at startup would race | An init container per host (the same race, per pod) |

| D34 | **CI:** product-ci builds every image on every pull request ([ADR-0036](../adr/0036-trunk-based-development.md)); a new `lab` workflow runs `lab up` in kind with a smoke test on pull requests that touch deployment files, and nightly | A broken chart is caught on the pull request that broke it | Nightly only |

## Definition of done

1. `dotnet run lab.cs -- up` builds the current source and brings up the whole system in a fresh
   cluster in under 15 minutes; `lab reset` in under 3; `lab down` leaves nothing behind
   ([ADR-0022](../adr/0022-disposable-lab-environment.md)).
2. Every flow from M1 works in the cluster: browse, hold, check out, pay on LocalPay, tickets,
   email.
3. PublicApi, WebhookIngress and Workers run as several instances; the Scaling Lab shows them
   and changes PublicApi's count under load without failed requests.
4. A rollout under constant load causes under 0.1% errors (T10).
5. A deploy during an on-sale is refused.
6. CI builds every image on every pull request; the lab workflow passes.
7. Every new decision has an ADR.

## Demo script (about 15 minutes, one presenter)

1. `dotnet run lab.cs -- up` was run before the demo (a few minutes); `status` lists what runs.
2. The Aspire Dashboard: each instance of PublicApi, WebhookIngress and Workers as its own replica.
3. The fan site: a purchase, exactly as under Aspire; the trace crosses instances.
4. The Scaling Lab: load at 100 requests/s; the instances panel shows three PublicApi instances.
   Raise the count to five and lower it to two: no failed requests.
5. A rollout under load (DP2): new instances start, old ones drain, errors stay at zero.
6. A deploy during an on-sale is refused (DP4).
7. `lab down`: nothing left.

## Risks

- **Memory.** The lab needs about 5 GB in M2 and grows in M3. Docker Desktop has 16 GB on the
  presenter's laptop.
- **Offline demos.** `lab up` pulls base images, charts and platform images. Run it once online
  the day before; later runs use the cache.
- **Ports.** The lab and Aspire use the same localhost ports (D28), so only one of them runs
  at a time.
- **On one laptop, more instances share the same CPU and database.** They show how scaling
  works, not more capacity.
